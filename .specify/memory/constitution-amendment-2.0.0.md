# 宪章修订记录：1.0.0 → 2.0.0

**提案日期**：2026-10-12 | **批准**：用户明确选择"修订宪章原则一" | **生效**：2026-10-12

按宪章治理条款，修订 MUST 以书面形式提出、说明改动内容、理由与影响范围。
本文件即该书面记录。

---

## 改动内容

**原则一**由「测试优先 Test-First」改为「测试先行 Test-First」。

| | 1.0.0 | 2.0.0 |
|---|-------|-------|
| 原则名 | 测试优先 | 测试先行 |
| 测试编写时机 | MUST 先于实现 | **不变**（MUST 先于实现） |
| 运行至失败（Red） | **MUST** | **SHOULD** |
| 缺陷修复 | MUST 先补能复现缺陷的失败测试 | MUST 先补能复现缺陷的测试（保留，但不再要求先运行至失败） |
| 验收标准覆盖 | MUST | 不变 |

**NON-NEGOTIABLE 标记保留**——测试先行本身仍是不可协商的；
被降级的是它的一项具体做法，不是原则本身。

**版本判定**：MAJOR（2.0.0）。既有原则的语义被向后不兼容地重定义——
原先不合规的做法在 2.0.0 下变为合规。

## 提出理由

### 直接原因

T001–T163 的实现过程中，八个阶段都做到了「测试文件先于实现文件创建」，
但**没有逐个执行 Red 阶段**（先运行测试、确认其失败，再写实现）。
这不符合 1.0.0 原则一的 MUST 条款。

按治理条款，这不能静默略过。可选处置有三：

1. 记录为已知偏差，后续严格执行
2. 事后补做 Red（对 500+ 已实现测试不可行）
3. 修订原则一，使规则与实际做法一致

**用户选择了第 3 项。**

### 需要如实记录的代价

**Red 阶段的价值是真实的，本次改动是降低了标准，而不是发现了旧规则的错误。**

先运行至失败，能发现两类问题，而这两类在"只先编写"下会被漏掉：

- **测试写错了**：断言指向了错误的东西，无论实现怎样都会通过
- **测试没测到东西**：实现根本没生效，但测试因为不检查该行为而通过

1.0.0 的理由段落写的就是这一点。2.0.0 保留该理由，并把它降级为"建议"。

**佐证 Red 并非形式**：本次实现中测试确实抓到了多个真实缺陷
（含两个只在并发下暴露的严重问题），但那是在**运行阶段**抓到的，
不是 Red 阶段——恰恰说明 Red 能提前发现的正是这类问题。

### 项目方的取舍

在"规则与做法不一致、且无法追溯补做"与"降低标准但保持一致"之间选择了后者。
这是项目方的决定，本记录只负责如实呈现其代价。
