# 标签管理系统（Label Management System）宪章

## 核心原则

### 一、测试先行 Test-First（NON-NEGOTIABLE）

所有功能开发 MUST 遵循 TDD：先写测试，再写实现。

- 测试 MUST 在实现之前编写。实现完成时，其测试 MUST 已经存在。
- 提交的测试 MUST 覆盖该改动的验收标准；每一条验收标准 MUST 至少对应一个可执行测试。
- 仅当改动为纯文档、纯配置或纯样式且不含逻辑分支时，MAY 豁免测试先行。
- 缺陷修复 MUST 先补一个能复现该缺陷的测试，再修实现。
- **SHOULD** 在编写实现之前运行一次新测试并确认其失败（Red）。这是发现「测试写错了」
  与「测试根本没测到该行为」最直接的手段——这两类问题在只编写不运行的情况下会静默通过。

**理由**：测试先行把需求的模糊之处提前暴露为具体断言，是防止「实现完成但需求理解错误」最直接的机制，也使人机协作有可验证的成功判据而非主观判断。

**关于 Red 阶段的降级（2.0.0 修订）**：1.0.0 要求「MUST 先运行并失败」，
2.0.0 将其降为 SHOULD。这是**降低标准**，不是发现旧规则有误——
Red 能提前发现的问题（断言写错、测试未覆盖目标行为）依然存在，只是不再强制拦截。
修订理由与代价见 `.specify/memory/constitution-amendment-2.0.0.md`。

### 二、不猜测，先问清楚（NON-NEGOTIABLE）

信息不足时 MUST 停下来澄清，禁止带着假设开工。

- 需求、数据模型、异常分支或验收标准存在歧义时，MUST 先列出歧义点并提问，而不是自行选择一种解释继续实现。
- 存在多种合理解读时，MUST 全部列出并说明取舍，由用户决定；禁止静默挑选。
- 实现前 MUST 显式声明所做假设；假设未被确认的，视为未澄清。
- 发现更简单的做法时 SHOULD 主动提出并说明理由，而非默默按原路径实现。

**理由**：一次澄清的成本远低于按错误假设写完后返工的成本；静默假设会让错误在多层实现中扩散，事后定位代价极高。

### 三、架构变更须先确认（NON-NEGOTIABLE）

涉及重大架构调整时 MUST 先获得用户明确确认，确认之前 MUST NOT 动手。

- 「重大架构调整」包括但不限于：新增或拆分服务 / 进程、更换框架或关键技术选型、改变双端职责边界、改变跨端通信方式、变更数据存储方案、引入新的中间件或外部依赖。
- 此类变更 MUST 先产出方案（含影响范围与备选方案），待用户明确批准后再实施。
- 未经确认 MUST NOT 直接修改目录结构、模块划分或依赖关系。
- 若实施过程中发现需要偏离已确认方案，MUST 停下并重新确认，而非就地扩大改动范围。

**理由**：架构决策的影响面横跨两端与全部后续 feature，返工成本随实现深度非线性增长；先确认可把代价控制在纸面而非代码。

### 四、简单优先 Simplicity First

实现 MUST 是解决问题的最小代码，不写投机性设计。

- MUST NOT 实现需求之外的功能。
- MUST NOT 为一次性代码引入抽象层。
- MUST NOT 添加未被要求的「灵活性」或「可配置性」。
- MUST NOT 为不可能出现的场景编写错误处理。
- 自检标准：若资深工程师会认为该实现过度复杂，MUST 简化后再提交。

**理由**：未被要求的能力没有对应测试与验收标准，是缺陷与维护成本的净来源。

### 五、外科手术式修改 Surgical Changes

改动 MUST 只触及完成需求所必需的代码。

- MUST NOT 顺手「改进」相邻的代码、注释或格式。
- MUST NOT 重构未被要求且未损坏的部分。
- MUST 遵循既有代码风格，即使个人偏好不同。
- 改动导致自己引入的孤儿代码（不再被使用的 import、变量、函数）MUST 清理；既有的历史死代码 MUST NOT 删除，只 MAY 提示。
- 判据：每一行改动都 MUST 能直接追溯到用户的需求。

**理由**：无关改动会污染 diff、加大评审成本，并让缺陷归因变难。

### 六、双端分离架构 Two-Tier Architecture

系统 MUST 由两个独立客户端构成，各自技术栈固定。

- **管理后台（Admin）**：后端 MUST 使用 Python + FastAPI，前端 MUST 使用 Vue。
- **打印软件端（Print Client）**：MUST 使用 Electron 实现。
- 打印软件端 MUST NOT 直接连接后台数据库；所有业务数据的读写 MUST 经由管理后台提供的 HTTP API。
- 两端 MUST NOT 共享运行时或进程；任何一端 MUST NOT 直接依赖另一端的内部实现细节。
- 数据模型、API 契约或职责边界的变更属于跨端契约变更，MUST 遵守原则三（变更前先确认），并 MUST 两端同步更新。
- 打印软件端 MAY 保留本地非业务数据（如设备配置、打印偏好、离线缓存），但 MUST NOT 将本地存储作为业务数据的权威来源。

**理由**：单一数据入口保证业务规则与权限校验集中在后端，避免两端逻辑漂移；固定的技术栈边界让两端可以独立开发、测试与发布。

## 技术栈与架构约束

- **仓库结构**：本仓库同时容纳管理后台与打印软件端。两端的代码、依赖清单与构建配置 MUST 相互隔离，MUST NOT 交叉引用。
- **技术栈变更**：原则六中已固定的技术栈（FastAPI / Vue / Electron），变更 MUST 先确认（原则三）。
- **新增依赖**：两端各自新增运行时依赖时，MUST 说明用途；引入新的中间件、外部服务或关键技术选型 MUST 先确认（原则三）。
- **配置与密钥**：密钥、连接串等敏感配置 MUST NOT 硬编码进源码，MUST 通过环境变量或配置文件注入，且 MUST NOT 提交到仓库。
- **跨端契约**：管理后台暴露的 HTTP API 是两端之间的唯一契约面。契约变更时 MUST 更新对应的契约测试（原则一）。

## 开发工作流与质量门禁

- **开发步骤**：澄清需求（原则二）→ 判断是否属于架构变更（原则三）→ 先写测试（原则一，SHOULD 先确认失败）→ 实现 → 重构 → 验证。
- **多步任务的执行计划**：执行前 MUST 给出简短计划，每步标注验证方式，格式为：

  ```text
  1. [步骤] → verify: [检查项]
  2. [步骤] → verify: [检查项]
  3. [步骤] → verify: [检查项]
  ```

- **提交门禁**：改动 MUST 通过该端全部既有测试后才可提交；测试失败时 MUST 在提交说明中如实说明，MUST NOT 以「已完成」表述。
- **评审要点**：评审 MUST 核验本宪章六条原则；复杂度 MUST 有理由；评审者 MUST 确认 diff 中每一行改动都能追溯到需求。
- **Spec Kit 流程**：功能开发 MUST 走 `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` 流程，`plan.md` 中的 Constitution Check 一节 MUST 逐条对照本宪章填写。

## 治理

- **效力**：本宪章优先于其他一切开发惯例与个人偏好；与本宪章冲突的实践 MUST NOT 执行。运行时的具体开发指引以 [CLAUDE.md](../../CLAUDE.md) 为准，二者冲突时以本宪章为准。
- **修订程序**：修订 MUST 以书面形式提出，说明改动内容、理由与影响范围；须经用户明确批准后方可生效。修订 MUST NOT 静默进行。
- **版本策略**：版本号采用语义化版本 `MAJOR.MINOR.PATCH`。
  - **MAJOR**：原则被移除，或既有原则的语义被向后不兼容地重定义。
  - **MINOR**：新增原则或章节，或既有指引被实质性扩充。
  - **PATCH**：措辞澄清、错别字修正、不改变语义的细化。
- **合规审查**：每次修订都必须产出 Sync Impact Report，列明版本变更、原则增删改与后续 TODO。所有 feature 的实现计划 MUST 包含 Constitution Check；无法满足的原则 MUST 在计划中显式记录并说明理由，MUST NOT 默认豁免。
- **解释权**：原则含义存在歧义时，按原则二处理——先澄清，再执行。
