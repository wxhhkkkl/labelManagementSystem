# Phase 0 研究报告：打印管理系统

**功能**：[spec.md](./spec.md) | **日期**：2026-10-12

本文件记录进入设计前必须解决的技术未知项。每项给出结论、理由与被否决的备选方案。

---

## R1. 补打任务下发通道：工位端轮询

**Decision**：工位软件以固定周期轮询后台的"待执行任务"接口领取补打任务；不使用长连接。

- 轮询周期：**5 秒**（可配置）。
- 请求体携带工位标识与该工位最近一次已领取的任务序号，服务端仅返回新任务。
- 单次轮询为轻量查询：命中无任务时返回空数组，不产生写操作与日志。
- 任务领取采用**原子领取**（`UPDATE ... SET claimed_by=?, claimed_at=? WHERE id=? AND claimed_by IS NULL`），避免同一工位多实例重复领取。

**离线判定（关键连带影响）**：因无长连接，"原工位不可用"（FR-056）**不能**靠连接断开感知，改由**心跳超时**推断：

- 工位软件每 5 秒上报一次心跳（可与轮询合并为同一请求）。
- 服务端记录每个工位最后心跳时间；超过 **30 秒**（心跳 6 次未达）即判定该工位离线。
- 发起补打时，目标工位处于离线判定中 → 按 FR-056 拒绝补打并提示"原工位已离线"。
- 该判定同时用于 FR-071 的"打印服务未启动"提示之外的**设备级**在线状态展示。

**代价（必须在验收中体现）**：离线判定存在最长 30 秒的延迟窗口。即工位实际掉线后 30 秒内，后台仍会认为它在线并接受补打，任务会滞留到该工位恢复后才执行。这是选择轮询换取"无连接状态管理"的直接代价。

**Rationale**：工位端网络环境位于工厂内网，可能存在 NAT 与代理；轮询不依赖长连接保活，部署与排障都更简单。系统的实时性要求并不苛刻——补打由管理员人工发起，秒级延迟可接受；而正常打印路径完全由工位端主动发起，不受本决策影响。

**Alternatives considered**：
- 常驻 WebSocket 长连接：实时性最好且可即时感知离线，但服务端需维护连接表、心跳与重连逻辑；本期在"简单优先"（宪章原则四）下否决。
- 短轮询混合（业务 REST + 10 秒补打轮询）：本质与轮询相同，只是把周期拆成两档，增加配置面而无实质收益。

## R2. 数据库：MySQL 8

**Decision**：MySQL 8.0+，使用 InnoDB 与 `utf8mb4` 排序规则；批量取码与并发抢码依赖 `SELECT ... FOR UPDATE SKIP LOCKED`。

**Rationale**：团队储备与运维成本优先。InnoDB 行级锁足以支撑 FR-044 的并发防重：同一码的并发打印请求在事务内 `SELECT ... FOR UPDATE` 串行化，后者必然读到"打印中/已打印"从而被拒绝。

**必须遵守的约束（否则并发控制失效）**：
- MySQL 版本 MUST ≥ 8.0.1（`SKIP LOCKED` 自 8.0 起可用，用于 FR-025 的批量取码，避免多工位并发分配时的锁等待）。
- 码表的状态流转 MUST 在事务内完成"读-判-写"，MUST NOT 采用"先查询再更新"的两段式写法。
- 隔离级别使用默认的 REPEATABLE READ；`SELECT ... FOR UPDATE` 已能覆盖本场景，MUST NOT 为了规避幻读而升级到 SERIALIZABLE（会显著降低并发）。
- 时间字段统一使用 `DATETIME` 存 UTC，由应用层转换时区。

**Alternatives considered**：
- PostgreSQL：`SKIP LOCKED` 与 JSONB 更成熟，但与团队储备不符。
- SQLite：部署最简，但单写者模型无法支撑 50 工位并发打印与 10 万行导入，且不满足 FR-044 的并发语义。

## R3. 10 万行导入：异步任务 + 进度查询

**Decision**：导入走"上传即返回批次号 → 后台处理 → 前端轮询进度"的异步模型；本期使用**数据库任务表 + 服务端进程内队列**，不引入 Redis/Celery。

**关键设计**：
- 上传接口仅做落盘与批次登记，立即返回 `batch_id`，不解析文件内容。
- 解析任务由服务端进程内的单工作线程消费（导入是重 I/O + 重 CPU 操作，并发多个导入没有收益且会拖垮服务端）。
- 进度以**已处理行数 / 总行数**的形式写入批次记录，前端每 2 秒轮询一次进度接口。
- 服务端重启后，处于"处理中"状态的批次 MUST 被标记为"已中断"，允许用户重新发起——不实现断点续传（本期不做）。
- Excel 解析使用 `openpyxl` 的 `read_only=True` 流式模式，MUST NOT 一次性 `load_workbook` 全量载入（10 万行会占用数百 MB 内存）。
- 校验按 FR-014／FR-015／FR-017 执行：两文件码集合一致 → 逐行格式与长度 → 全库唯一性。失败明细分批写入，避免内存中堆积 10 万条错误对象。
- 入库使用 `executemany` 批量插入（每批 1000 行），MUST NOT 逐行 `INSERT`。

**Rationale**：10 万行的解析与校验远超常见网关的 60 秒超时窗口；同步处理在规格的 SC-003 下会变成"运气好才成功"。异步化同时天然贴合 FR-018 要求的批次记录。不引入 Redis/Celery 是因为本期只有一个后台任务类型，进程内队列 + 数据库状态表已足够，符合宪章"简单优先"。

**Alternatives considered**：
- 同步处理：实现最简，但在 10 万行规模下不可靠，与 SC-003 冲突。
- Celery + Redis：生产级、可水平扩展，但多一个中间件要部署运维；待导入量或任务类型增长后再演进。

## R4. 认证：统一 JWT

**Decision**：管理后台与工位软件使用同一套 JWT 认证；访问令牌有效期 2 小时，刷新令牌 7 天。

- 令牌载荷包含 `user_id`、`role`、`company_id`（工位操作员另含 `workstation_id`）。
- 权限校验在服务端统一中间件完成，按 FR-006 强制注入组织过滤条件；**组织隔离 MUST 在服务端强制执行，MUST NOT 依赖前端过滤**。
- 工位软件侧令牌存入 Electron 的安全存储（`safeStorage`），MUST NOT 明文落盘。
- 工位软件绑定工位的身份（FR-069）与操作员身份分离：工位标识来自本机配置，操作员身份来自登录令牌，二者共同构成打印记录。

**Rationale**：两端同一套中间件意味着 FR-006／FR-007 的组织隔离逻辑只实现一次，避免两套认证路径在权限校验上走叉。服务端无状态便于后续横向扩展。

**取舍**：JWT 无法即时吊销。本期通过"短有效期 + 刷新令牌"控制风险；强制下线（如停用账号后立即失效）依赖每次请求校验账号状态字段，而非依赖令牌失效——**账号停用 MUST 在每次请求时实时校验，不能仅靠令牌过期**。

**Alternatives considered**：
- 浏览器 Cookie + 工位端 JWT：浏览器端更抗 XSS，但两套路径需各写一遍中间件与测试。
- 服务端会话：吊销最简单，但 Electron 端处理 Cookie 体验差。

## R5. 标签渲染与打印：Windows 驱动 + 静默打印

**Decision**：模板元素定义以结构化 JSON 存储；工位软件将 JSON 渲染为 HTML/CSS 页面，由 Electron 以**指定纸张尺寸**静默打印到绑定打印机。

- 模板 JSON 至少包含：纸张宽高（毫米）、元素数组（类型、坐标、尺寸、字体、字号、对齐、动态字段名）。
- 渲染使用固定 DPI 换算（毫米 → 像素按 96 DPI 基准，由打印时的 `scaleFactor` 校正），MUST NOT 依赖 CSS 的自动缩放。
- 静默打印使用 Electron `webContents.print({ silent: true, deviceName, pageSize })`，`pageSize` 取模板定义的毫米尺寸。
- 纸张尺寸与打印机型号的匹配关系由 FR-055 的适配矩阵记录。

**Rationale**：FR-073 明确"新型号接入以驱动安装为基础，原则上无需修改系统代码"——这直接指向走 Windows 打印驱动路径，而非生成 ZPL/EPL 等原生指令（后者与具体型号强绑定，每接一个新型号都要改代码）。同时 OI-01（打印机型号清单）尚未提供，驱动路径是唯一能在型号未知时先推进的方案。

**风险与回退**：若后续型号适配发现驱动路径无法满足精度（如热敏标签机对走纸与切纸的精确控制），则对个别型号增加"原生指令插件"作为补充通道。FR-072 已为此预留驱动插件机制，故不需要在渲染层做改动。

**Alternatives considered**：
- 直接生成 ZPL/EPL/ESC-POS 指令：对热敏标签机精度最高，但与型号强绑定，且 OI-01 未定，无法在本期落地。
- 服务端生成 PDF 再下发打印：跨平台一致性好，但增加了服务端依赖与传输量，且静默打印仍需本机驱动，收益不明显。

## R6. 模板可视化编辑：Vue 拖拽方案

**Decision**：使用 `vue-draggable-plus`（或同类的 `vuedraggable`）实现元素拖拽定位，画布按毫米坐标定位并叠加缩放比例，实时预览使用同一套渲染规则。

**关键约束（受宪章原则六约束，已修正）**：管理后台的编辑器预览与工位端的实际打印，必须产出**完全一致**的版面，否则"所见"与"所打"不一致。最初拟"抽出共享渲染模块、两端各自引用"，但**这违反宪章原则六**——"两端的代码、依赖清单与构建配置 MUST 相互隔离，MUST NOT 交叉引用"。

因此改为：**渲染规则以契约定死，两端各自独立实现**。契约见
[contracts/template-rendering.md](./contracts/template-rendering.md)，规定毫米→像素换算基准、
打印缩放因子、元素类型、样式属性与对齐规则。两端各自实现并**各自持有针对同一契约的测试**；
契约变更时两端同步更新（宪章原则六：跨端契约变更须两端同步）。

**代价（明确记录）**：同一套规则被实现两次。这是为满足"两端不得交叉引用"付出的成本。
缓解手段是契约文档足够具体（精确到换算公式与元素属性），并有测试用例同时约束两侧。

**Rationale**：FR-038 要求拖拽定位 + 实时预览 + 打印预览；后端不参与渲染可避免服务端引入图形依赖。

**Alternatives considered**：
- 共享代码模块（原方案）：实现成本最低，但与宪章原则六冲突，否决。
- 服务端渲染模板预览图（Pillow/ReportLab）：能保证绝对一致，但服务端需引入图形库，且打印仍走客户端渲染，等于仍是两套渲染实现——成本更高而一致性收益不完整。

## R7. 组织数据隔离：服务端强制过滤

**Decision**：所有列表与详情查询在服务端按登录用户角色注入强制过滤条件，不允许"先查全量再过滤"。

- 总部管理员：无组织过滤。
- 子公司管理员与工位操作员：强制附加 `company_id = <本用户所属公司>`。
- 工位操作员对打印任务的额外限制：只能操作本公司码（码在公司内共享，见 spec 假设）。
- 单对象访问（按 ID 取码/记录）同样 MUST 校验归属，MUST NOT 仅依赖列表过滤。

**Rationale**：对应 SC-007（子公司查询结果中他公司数据出现 0 次）与 FR-007（越权一律拒绝并记录）。这是可被测试直接覆盖的安全属性，实现位置必须收敛到中间件/查询基类一处。

**Alternatives considered**：依赖前端过滤——否决，等同于无隔离。

## R8. 测试策略（宪章原则一：TDD 不可协商）

**Decision**：三层测试，全部先写后实现。

| 层级 | 工具 | 覆盖对象 |
|------|------|----------|
| 单元 | `pytest` | 状态机流转（FR-077/078）、码值校验（FR-015）、模板渲染换算 |
| 集成 | `pytest` + 真实 MySQL 实例 | 导入批次、分配与回收、打印预占-确认、并发抢码、组织隔离（越权用例） |
| 契约 | `pytest` + `httpx` | 管理后台与工位端共用的 HTTP 接口契约（见 `contracts/`） |
| 前端单元 | `vitest` | Vue 组件与模板渲染规则 |
| 端到端 | `playwright`（管理后台）；工位端关键路径手工验收 | 主流程冒烟 |

**必须优先以失败测试覆盖的高风险点**（对应 spec 的核心控制点）：
1. **防重复打印**（FR-042/FR-043）：已打印的码再次打印必被拒绝；并发同一码仅一方成功。
2. **超时回退**（FR-047）：打印中超过时限自动回退且不计补打；同时验证"实际已出纸但回执丢失"这一已知风险场景的记录留痕。
3. **补打派发**（FR-055/FR-056）：补打落到原工位；原工位离线时拒绝且码状态不变。
4. **组织隔离**（FR-006/FR-007）：子公司账号越权访问他公司码、记录、报表一律拒绝。
5. **导入成对校验**（FR-014）：两文件码集合不一致时整批拒绝并输出差异明细。
6. **产品停用前置校验**（FR-010）：存在"已分配未打印"码时停用被拒绝。

**Rationale**：上述六点是系统"防重复、可追溯、不越权"的业务主张所在，任何一处回归都直接破坏项目目标。它们的测试必须在实现之前编写并先运行至失败。

**Alternatives considered**：仅做端到端测试——反馈太慢，无法在实现过程中驱动设计。
