## 一、启动后台

```bash
# 后端
cd backend
python -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
export DATABASE_URL="mysql+pymysql://user:pass@localhost:3306/lms"
alembic upgrade head          # 建表
uvicorn app.main:app --reload # http://localhost:8000

# 前端
cd ../admin-web
npm install
npm run dev                   # http://localhost:5173
```

**验证**：访问 `http://localhost:8000/docs` 应能看到 OpenAPI 文档，且 `/api/v1/auth/me`
在未带令牌时返回 `401`。

## 三、核心场景验证

以下六个场景直接对应 [research.md R8](./research.md) 列出的高风险点。每个场景都 MUST 有
对应的自动化测试；此处描述如何**手工复现**，用于验收与排障。

### 场景 1：导入成对校验（FR-014）

1. 准备两个 Excel：`codes.xlsx` 含码值 `A001`~`A010`；`mapping.xlsx` 只含 `A001`~`A005`（集合不一致）。
2. 以总部管理员登录 → 上传两个文件。
3. **预期**：批次状态终态为 `failed`，失败明细可下载并列出不一致的码值；**码池中不产生任何新码**。

**反向用例**：两文件均为 `A001`~`A010` → 批次 `succeeded`，10 个码进入码池，状态 `unallocated`。

### 场景 2：分配与并发取码（FR-025 / FR-044）

1. 给某产品导入 5000 个码。
2. 按"公司 + 产品 + 数量 3000"发起分配。
3. **预期**：生成分配单；3000 个码变为 `allocated` 且归属该公司；剩余 2000 个仍为 `unallocated`。
4. **并发验证**：并行发起两个各 3000 的分配请求 → 只有一个成功，另一个返回可用量不足。

### 场景 3：防重复打印（FR-041 ~ FR-044）—— 系统核心控制点

1. 工位软件绑定工位 A，以操作员账号登录。
2. 按产品查看可打印码，选 1 个发起打印。
3. **预期**：码状态变为 `printing`，本地打印服务出纸。
4. 确认成功 → 码变 `printed`，`PrintLog` 生成一条 `print_type='first'`。

**关键断言（三条都必须成立）**：
- 再次对该码发起打印 → 返回 `409 CODE_ALREADY_PRINTED`，**不出纸**。
- 从工位 B（同公司）并发发起同一码打印 → 仅一方成功，另一方 `409 CODE_LOCKED`。
- 从另一家公司（若已分配到该公司）看不到该码。

### 场景 4：打印失败回退 vs 补打（FR-045 ~ FR-053）

1. 发起打印后，在工位端**不确认成功**，改为上报 `outcome='failed'`（模拟缺纸）。
2. **预期**：码回退为 `allocated`，`print_count` 不变，**`reprint_count` 也不变**（不算补打）。
3. 该码可再次正常打印。
4. 正常打印成功后，由子公司管理员发起补打并填原因。
5. **预期**：`reprint_count` 变为 1；`PrintLog` 新增一条 `print_type='reprint'`；
   **补打任务出现在该码原工位**的任务轮询结果中。

### 场景 5：补打派发与离线拒绝（FR-055 / FR-056）—— 轮询模型的验证重点

1. 码在工位 A 打印成功后，**停止工位 A 的心跳**。
2. 等待 **> 30 秒**（R1 的离线判定窗口）。
3. 从后台对该码发起补打。
4. **预期**：返回 `409 WORKSTATION_OFFLINE`，**且该码状态保持不变**（不进入补打流程）。
5. 恢复工位 A 心跳，重新发起补打 → 成功创建任务；工位 A 在下一次轮询（≤5 秒）内领取并出纸。

**延迟窗口验证（必须记录为已知行为）**：在停止心跳后的 **30 秒内**发起补打，系统仍会接受并
创建任务，任务会滞留到工位恢复后才执行。这是选择轮询的既定代价，**不是缺陷**，验收时不应
作为失败项。

### 场景 6：超时回退与重复出纸风险（FR-047 / FR-048）

1. 发起打印（码进入 `printing`）后，**在工位端不做任何确认**（模拟回执丢失或进程崩溃）。
2. 等待超过配置的超时阈值（默认 5 分钟；测试时可将 `PRINT_LOCK_TIMEOUT_SECONDS` 调至 10 秒）。
3. **预期**：码自动回退为 `allocated`；`PrintLog` 生成 `result='timeout_reverted'`；
   `reprint_count` **不变**（不计补打）。
4. 该码可被再次打印。

**已知风险断言**：若第 1 步实际已出纸，第 4 步会造成**重复出纸**。测试 MUST 断言
`timeout_reverted` 记录已写入 `PrintLog`，以保证该情形事后可审计——这是 spec 中明确接受的取舍。

### 场景 7：组织隔离与越权拒绝（FR-006 / FR-007 / SC-007）

1. 建立甲、乙两家公司，各自有码与打印记录。
2. 以乙公司管理员登录。
3. **预期（逐项断言）**：
   - 看板、打印明细、补打/作废台账中**甲公司的数据出现 0 次**。
   - 直接按 ID 请求甲公司的码详情 → `403 FORBIDDEN_SCOPE`。
   - 对甲公司的码发起补打或作废 → `403 FORBIDDEN_SCOPE`。
   - 访问 `/api/v1/audit-logs` → `403 FORBIDDEN_SCOPE`（仅总部可查，FR-062）。
   - 上述每次拒绝都 MUST 在 `AuditLog` 中留下 `result='denied'` 记录。

### 场景 8：产品停用前置校验（FR-010）

1. 某产品有 100 个已分配到公司的未打印码。
2. 总部尝试停用该产品。
3. **预期**：返回 `409 PRODUCT_HAS_ALLOCATED_CODES`，产品状态不变。
4. 回收或作废该产品的全部在途码后再次停用 → 成功。

## 四、性能验证（SC-003 / SC-005 / SC-013）

| 指标 | 验证方法 | 目标 |
|------|----------|------|
| 导入吞吐 | 导入 10 万行码清单 + 对照关系 | 完成并输出成功/失败明细（SC-003） |
| 批量打印下发 | 一次任务 500 码 | 60 秒内完成下发（SC-005） |
| 列表查询 | 码库填充至百万级后查询码池与打印明细 | 3 秒内返回（SC-013） |
| 并发工位 | 模拟 50 个工位同时心跳 + 打印 | 无错误，无需人工干预（SC-008） |

**注意**：SC-003 的"一次操作"在异步模型下指"上传 → 后台处理完成 → 得到明细"的完整过程。
验证时 MUST 通过批次进度接口确认终态，MUST NOT 以 HTTP 请求返回时间作为判据。
